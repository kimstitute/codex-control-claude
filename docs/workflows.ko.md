# 제안 및 검토 워크플로우(범위 제한)

버전 0.6은 고정된 로컬 워크플로우 하나를 추가합니다: 워커 제안 → 독립적인 Fable
검토 → 선택적 워커 수정 → 재검토 → Codex 결정. 워커는 자신의 어사인먼트에
명시된 모델을 사용하며, 보통 Sonnet입니다. 플래너/아키텍트 워커는 Fable을
사용할 수 있습니다. 두 에이전트 모두 도구와 MCP가 비활성화된 상태로 공급된
텍스트를 전달받습니다.

## 생성, 실행, 조회

어사인먼트 형식과 `claude_control` 헬퍼는 [CLI 가이드](cli.ko.md)를
참고하세요. 워커 역할은 `executor`, `planner`, `architect` 중 하나여야 합니다.

```bash
claude_control workflow create --assignment-file /absolute/path/assignment.json \
  --operation-id proposal-workflow-1 \
  --max-revisions 2 --max-calls 6 --dispatch-window-seconds 900
claude_control workflow run --workflow <workflow-uuid> --once
claude_control workflow run --workflow <workflow-uuid> --until-idle --max-seconds 60
claude_control workflow status --workflow <workflow-uuid>
claude_control overview --attention
```

생성 시 두 멤버 태스크, 고정 정책, 초기 큐 항목이 기록됩니다. 이 과정에서
모델 호출은 발생하지 않습니다. 워크플로우 UUID를 저장해 두세요. 동일한 생성
요청을 반복하면 같은 워크플로우가 반환되며, 정책이 변경된 경우에는 충돌이
발생합니다.

`run --once`는 완료된 작업을 진행시키고 한 번의 승인(admission) 패스를
수행합니다. `--until-idle`에는 0~3600 범위의 유한한 `--max-seconds`가
필요합니다. 이는 현재 코디네이터 호출을 제한하는 값입니다. 워크플로우 자체의
지속적인 디스패치 윈도우는 별개의 제한입니다. 코디네이터 종료 후 계속하려면
같은 워크플로우를 다시 실행하세요. 이미 예약된 실행은 관찰만 될 뿐 다시
시작되지 않습니다. 이 명령은 지정된 워크플로우만 디스패치합니다. 일반적인
FIFO 디스패치 역시 동일한 승인 가드를 마주치는 모든 워크플로우 큐 항목에
적용합니다.
유한 루프는 다른 실행 중인 작업이 점유한 용량을 기다리되, 그 작업들의 대기
중인 항목은 디스패치하지 않습니다.

상주하는 코디네이터나 자동 Codex 웨이크업은 없습니다. `status`와 `overview`는
실행 증거를 갱신하지만 스테이지를 생성하거나 모델을 호출하지 않습니다.
Overview에는 워크플로우 예산, 태스크 상태, 해결되지 않은 실행, 이벤트
커서가 포함됩니다. 이벤트 ID가 순서를 정의하며, 실시간 타임스탬프는 참고용일
뿐입니다.

## 정책과 예산

| 설정 | 기본값 | 허용 값 | 의미 |
|---|---:|---|---|
| `max-revisions` | 2 | 정수 0~10 | 최초 제안 이후 워커 수정 횟수 |
| `max-calls` | 6 | 정수 2~64 | 예약된 모델 턴 수(알 수 없거나 실패한 시도 포함) |
| `dispatch-window-seconds` | 900 | 유한 값 1~86400 | 첫 성공 예약 이후 새 예약이 허용되는 시간 |

첫 예약과 그 타임스탬프는 함께 커밋됩니다. 그 예약 이전의 큐 대기 시간은
윈도우를 소모하지 않습니다. 코디네이터를 재시작해도 카운터나 시간은
초기화되지 않습니다. 용량/크기 검증 실패는 호출 영수증이 커밋되기 전에
롤백됩니다. 커밋된 예약은 해당 워커가 결코 실행되지 않더라도 호출 한 건을
소모하며, 암묵적 환불이나 재시도는 일어나지 않습니다.

새 워커 수정에는 검토를 포함해 최소 2회의 호출이 남아 있어야 합니다.
모델은 제한 값을 늘리거나 역할, 멤버십, 의존관계를 변경할 수 없습니다.
윈도우는 영속화된 실시간 시각을 사용하며, 첫 예약 이전의 시계는 승인을
차단합니다. 윈도우가 만료되어도 이미 진행 중인 실행은 각자의 개별 타임아웃을
유지하며 완료될 수 있지만, 새 실행은 승인되지 않습니다. 이 윈도우는 전체
완료 기한이 아닙니다.
코디네이터가 윈도우 만료 후 재개될 때 완료된 검토가 대기 중이라면, 그
추천 결과는 여전히 기록됩니다. 실행이 여전히 활성 상태인 도중 만료가
감지되면 자동화는 중단되고, 최종 결과는 Codex가 나중에 확인할 수 있도록
남습니다. Codex는 완료된 검토를 확인하고 `task review`로 명시적으로 기록할
수 있습니다.

## 정확한 검토와 최종 승인

태스크 v5 입력은 워크플로우 정책, 기준 ID, 정확한 소스 태스크/리비전/실행/
결과 다이제스트를 고정합니다. 검토자 스테이지는 워커와는 다른 지속 세션을
사용합니다. 각 검토는 새로운 태스크 리비전을 가지며, 사용되지 않는 리뷰어
자리표시자 이후의 첫 검토도 마찬가지입니다. P3 메시지는 고정된 워커 결과를
검토로 전달하고, 수정 지시사항을 워커에게 되돌려 전달합니다. 원본 보고서는
그 메시지에 한 번만 나타나며, `workflow.source.message_id`가 정확한 소스
아이덴티티 및 다이제스트와 함께 그것을 식별합니다.

검토자는 일반적인 태스크 보고서에 더해 구조화된 `review` 객체를 반환합니다:

```json
{
  "target": {
    "task_id": "<worker-task-uuid>", "revision": 1,
    "run_id": "<worker-run-uuid>", "result_sha256": "<exact-result-digest>"
  },
  "recommendation": "approve",
  "criteria": {"1": {"verdict": "pass", "evidence": "Concrete supplied evidence."}},
  "unverified": [],
  "revision_instructions": ""
}
```

고정된 모든 기준 ID가 정확히 한 번씩 나타나야 합니다. 판정 값은 `pass`,
`fail`, `unknown` 중 하나입니다. 승인(approval)에는 모든 기준이 pass이고
미검증 항목이 없어야 합니다. `revise`에는 비어 있지 않은 수정 지시사항이
필요합니다. 다이제스트 누락/오류, 형식이 잘못된 보고서, 모순된 승인은 추가
모델 호출을 유발하지 않습니다.

에이전트 상태가 `complete`인 온전한 완료 보고서는 Codex의 승인 없이도
비공개 워크플로우의 `reported` 엣지를 해제할 수 있습니다. 오직 이 고정된
템플릿만 그러한 엣지를 생성할 수 있습니다. 일반적인 태스크 의존관계는
여전히 명시적인 승인을 요구합니다. 소스는 승인 시점에 재검증되며, 이력상의
보고서는 그 고정된 사본을 사용합니다.

`approve`는 검토 추천을 기록하고 `awaiting_codex` 상태를 이유
`approve_recommended`와 함께 반환합니다. 이는 승인 결정을 기록하지
않습니다. 워커 결과를 확인한 뒤 정확한 현재 리비전, 실행, 결과 다이제스트,
기준별 증거와 함께 [task accept](tasks.ko.md)를 사용하세요. 상태는 오직
해당 정확한 결과에 유효하고 명시적인 Codex 승인이 있을 때만 `accepted`로
보고됩니다. `accepted_revision`이 이를 식별하며, 검토의 대상(target)은
별도로 계속 조회할 수 있습니다.

## 중지와 복구

```bash
claude_control workflow stop --workflow <workflow-uuid> --operation-id stop-1
claude_control workflow status --workflow <workflow-uuid>
```

중지(stop)는 먼저 새 예약을 영속적으로 차단하고 대기 중인 멤버 항목을
취소한 다음, 기존의 관리형 실행 제어를 통해 취소를 요청합니다. 소유한
프로세스가 아직 해결되지 않은 동안에는 `stopping`을 반환하고, 종료가
확정되면 `stopped`를 반환합니다. 중단 후 정리를 재개하려면 stop을 다시
실행하거나 stopping 상태인 워크플로우를 다시 실행하면 됩니다. 알 수 없는
(unknown) 실행은 격리(quarantine) 상태로 남으며, 실행 종료가 확인된 후에는
해당 소유 PID 네임스페이스에서 기존의 `reconcile --run` 명령을 사용하세요.
unknown을 success로 바꾸거나 DB를 직접 편집하여 슬롯을 해제해서는 안 됩니다.

실패, 형식이 잘못되었거나 차단된 출력, 컨텍스트 불일치, 예산 소진, 알 수
없는 실행 종료는 모두 자동화를 `awaiting_codex` 상태로 종료시킵니다. 이
릴리스에는 워크플로우 재시도나 리셋이 없습니다. 산출물을 확인하고, 필요하면
reconcile을 수행하고, 워크플로우를 중지하거나, 유효한 현재 워커 결과를
명시적으로 승인하세요. 새 워크플로우를 만드는 것은 별개의 결정이며,
해결되지 않은 실행을 우회해서는 안 됩니다. 공개된 멤버의 submit/retry/
revise/enqueue/dequeue 명령과 공개 메시지 enqueue/cancel 명령은 고정된
템플릿을 변경할 수 없습니다.

## 호환성

새 스토어는 스키마 10을 사용합니다. 기존 스토어는 명시적인 오프라인
마이그레이션이 필요하며, 각 스키마 단계는 검증된 백업을 생성하고 이전의
태스크, 큐, 메시지, 워크플로우, 워크스페이스, effort, 결정(decision) 행을
보존합니다. 마이그레이션 전에 모든 클라이언트와 워커를 중지하고 알 수 없는
실행을 해결해야 합니다. [마이그레이션](tasks.ko.md#schema-and-migration)을
참고하세요.

레거시 세션과 태스크 계약 v1~v4는 기존 동작을 유지합니다. 이번 단계는 Claude
파일/셸 도구도, 호스트 간 작업 전달도 추가하지 않습니다.
