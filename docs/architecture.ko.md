# 아키텍처와 경계

## 구성 요소

```text
plugins/claude-control/
  .codex-plugin/plugin.json       플러그인 아이덴티티와 표시 정보
  assets/logo.png                프로젝트 마크
  skills/claude-control/         Codex 위임 워크플로우
  scripts/claude_control_cli.py   이식 가능한 진입점
  scripts/claude_control/
    cli.py                      JSON 명령 인터페이스
    store.py                    설정, SQLite 상태, 승인, 복구
    runner.py                   워커 및 소유 프로세스 그룹 생명주기
    protocol.py                 Claude 호출과 응답 검증
    assignments.py              버전이 지정된 역할 프롬프트와 어사인먼트/보고서 계약
    orchestration.py            다중 실행 관찰과 보고서 조회
```

플러그인은 자신의 디렉터리를 기준으로 코드를 상대 경로로 해석합니다. 런타임
설정, 프롬프트, 트랜스크립트, 데이터베이스는 플러그인 패키지 외부에
존재합니다.

## 요청의 생명주기

1. Codex가 제한된 프롬프트 파일, 모델, 역할, 프로젝트, 안정적인 요청 ID를
   제공합니다.
2. SQLite 트랜잭션이 호스트 아이덴티티, 요청 중복 여부, 세션 가용성, 공유
   동시성 제한을 확인합니다.
3. 전용 로컬 워커가 실행을 점유(claim)합니다. exec 래퍼가 Claude를 시작하기
   전에 그 프로세스 아이덴티티를 기록합니다.
4. Claude는 고정된 공급 텍스트 프로필과 명시적인 대화 ID로 실행됩니다.
5. 워커는 응답을 검증하고, 자신이 소유한 프로세스 그룹을 정리하고, 결과를
   원자적으로 기록하며, 그 다이제스트와 최종 상태를 기록합니다.
6. Codex는 결과를 가져와 사용하기 전에 그 내용을 검증합니다.

항상 실행 중인 코디네이터는 없습니다. 각 활성 작업에는 워커가 있으며, 이후
Codex 태스크는 영속화된 기록을 발견할 수 있습니다. 이 패키지는 채팅 턴이
끝날 때 자동으로 Codex를 깨우지 않습니다.

## 아이덴티티와 동시성

`delegate`는 공급된 JSON 어사인먼트를 정규화하고, 그 역할/모델을 해석한
뒤, 하나의 정규(canonical) JSON 봉투를 `start`와 동일한 예약·실행 경로로
전달합니다. 두 번째 태스크 상태 머신이나 리스(lease), 스케줄러가 추가되지
않습니다.
소스 분석과 이후 단계는 [OMX 도입 노트](omx-adoption.ko.md)를 참고하세요.

- 스토어는 자신의 호스트와 사용자에 바인딩되며, 별도의 설치 UUID를 가집니다.
- 관리되는 세션은 고정된 모델, 역할, 프로젝트를 가지며, 현재 백엔드 대화
  ID를 가집니다.
- 모든 실행은 명시적 재시작 이후에도 자신의 백엔드 ID를 보존합니다.
- 트랜잭션과 고유성 제약은 세션당 최대 하나의 활성 실행만 허용합니다.
- 대기 중, 실행 중, 중지 중, 불확실한 실행 모두 동시성 제한에 포함됩니다.
- 일치하는 중복 요청은 원래의 실행을 반환합니다. 충돌하는 재사용은
  거부됩니다.

## 프로세스 제어

워커는 프로세스 ID와 함께 Linux 시작 틱(start tick), 부팅 아이덴티티, PID
네임스페이스를 기록합니다. 취소는 소유 워커가 처리하는 영속적인 요청이며,
공개 CLI가 임의로 저장된 PID를 종료시키지는 않습니다.

워커는 신호를 보내고 그룹 정리를 확인하는 동안 프로세스 그룹 리더를
회수(reap)하지 않고 유지합니다. Linux의 parent-death 시그널과 exec
래퍼는 시작/워커 종료 경쟁 상태를 해결합니다. 컨트롤러가 실행 결과를 확정할
수 없는 경우, 자동으로 재시도하는 대신 `unknown`으로 기록하고 reconcile을
요구합니다.

이러한 메커니즘은 소유한 프로세스 그룹을 관리합니다. cgroup 샌드박스가
아니며, 그룹을 의도적으로 벗어나는 프로세스를 억제하지도 않습니다. 프로젝트
허용 목록(allowlist)은 선택된 작업 디렉터리를 제한할 뿐, 전체 파일 시스템
접근을 제한하지 않습니다.

## Claude 실행 프로필

컨트롤러는 안전 모드, 빈 설정 소스, 내장 도구 없음, 슬래시 명령 비활성화,
엄격하게 비어 있는 MCP 설정을 요청합니다. 명시적인 `--session-id` 또는
`--resume`을 사용하며, 가장 최근 대화를 암묵적 대상으로 삼지 않고 폴백
모델도 지정하지 않습니다.

관리자가 설정한 정책은 여전히 적용됩니다. 실시간 검증 결과, 프로젝트
SessionStart 훅이 이 프로필 하에서 실행되지 않음을 확인했습니다. 이는
테스트된 사례일 뿐, 컨트롤러가 가능한 모든 관리자 설정을 무시한다는 주장은
아닙니다.

Claude에 전달되는 환경은 제한되어 있습니다. 일반적인 HOME 기반 인증은
지원되지만, 사용자 지정 Claude 설정 위치와 API 키 환경 변수는 전달되지
않습니다. 로컬 컨트롤러는 인증을 프록시하거나 오프라인 모델 추론을 제공하지
않습니다.

## 결과 검증

성공하려면 일관된 형태의 제한된 JSON 스트림, 일치하는 세션 ID, 요청한
모델 계열과 일치하는 실제 어시스턴트 모델 증거, 성공적인 최종 결과, 도구
호출 없음, 프로세스 종료 코드 0이 모두 필요합니다. 초기화 메타데이터와
보조적인 모델 사용 정보만으로는 어떤 모델이 응답했는지 증명할 수 없습니다.

결과는 파일/디렉터리 동기화를 동반한 원자적 교체 방식으로 기록되며,
SHA-256 다이제스트가 저장됩니다. 상태 조회와 후속 승인 절차는 산출물의
무결성을 확인합니다. 이러한 검사는 결과 파일의 누락이나 변경을 감지할 뿐,
스토어 전체를 다시 쓸 수 있는 악의적인 사용자를 방어하지는 않습니다.

구조화된 보고서는 `claude-control.assignment.v1`을 사용합니다. 역할
스냅샷은 정규(canonical) ASCII JSON(동시에 UTF-8이기도 함)이며, 추가
개행 없이 표준입력(stdin)을 통해 전달됩니다. 보고서 조회는 그 프롬프트와
불변의 세션/실행 필드로부터 원래의 신규 세션 의도(intent) 지문을 재구성합니다.
검증은 오늘의 역할 카탈로그가 아니라 저장된 역할을 사용합니다. 알 수 없는
프로토콜 버전은 지원되지 않으며, 스냅샷이 변경되면 폐쇄적으로(fail closed)
실패합니다. 향후 의도-해시 알고리즘을 변경하려면 명시적인 호환성 처리가
필요하며, 그렇지 않으면 기존 보고서는 실패 처리됩니다.

오래된 상태 확인을 신뢰하지 않도록 보고서를 읽을 때 결과 바이트가 다시
검사됩니다. 형식의 유효성과 에이전트가 스스로 보고한 완료 여부는 실행 상태를
변경하거나 의미적(semantic) 승인을 부여하지 않습니다. 레거시 v1 보고서는
검토되지 않은(unreviewed) 상태로 남습니다. 버전 0.3은 명시적으로 추적되는
태스크 리비전을 위한 추가 전용(append-only) 결정 원장(ledger)을 v1 해석을
바꾸지 않고 추가합니다.

## 태스크 저장과 계약

스키마 4는 태스크, 불변 태스크 리비전, 명시적인 태스크-실행 계약 링크, 조작
중복 제거(operation deduplication), 추가 전용 검토 결정을 추가합니다.
리비전은 정규(canonical) 최종 프롬프트와 그 다이제스트, 고정된 역할
지시사항/모델/프로필, 예상되는 부모 실행/백엔드를 저장합니다. `task submit`은
이 컨텍스트를 확인하고 실행, 세션, 태스크 링크, 조작 응답을 하나의
`BEGIN IMMEDIATE` 트랜잭션으로 예약합니다. 워커는 커밋 이후에만
시작됩니다. 커밋되지 않은 산출물 디렉터리는 불활성(inert) 상태이며, 워커는
커밋된 실행 레코드와 성공적인 상태 점유(claim)를 요구합니다.

태스크 보고서는 `claude-control.task.v2`를 사용하며 태스크 UUID와 리비전을
식별합니다. 이들의 명시적인 DB 바인딩은 레거시 첫 실행 감지와 무관하게 모든
구조화된 후속 작업에 대해 동작합니다. 승인(approval)은 저장된 정확한 결과
바이트, 실제 모델/세션 증거, 보고서 상태, 현재 리비전 및 실행, 기준별
증거를 하나의 쓰기 트랜잭션에서 확인합니다. 검토 추천만으로는 어떤 승인도
부여되지 않습니다. 검토자 라벨은 감사(audit)용 메타데이터일 뿐, 인증된
보안 주체(principal)가 아닙니다.

태스크 상태는 영속화된 리비전, 실행, 결정으로부터 파생되며, 두 번째 완료
상태 머신을 만들지 않습니다. `queued/awaiting_submit`은 명시적인 제출을
요구하고, 큐에 있는 항목은 명시적으로 제한된 디스패치를 사용합니다. 재시도는
명시적이며, 시작되지 않았음이 증명된 최종 상태의 시도로만 한정됩니다. 알 수
없는(unknown) 실행은 슬롯을 유지하며 재시도할 수 없습니다.

마이그레이션은 명시적이고 오프라인으로 이루어집니다: 검증된 SQLite 백업,
영속적인 `migrating` 마커, 트랜잭션 기반 DDL/user_version, 설정 커밋,
저널 완료. 지원되는 클라이언트는 생명주기 락을 공유하고 DB/설정 버전을
확인하며, 예전 클라이언트는 중지되어야 합니다. 중단된 마이그레이션은
저널로부터 재개됩니다. 복구를 위해 자동 다운그레이드나 삭제는 사용되지
않습니다. [태스크 가이드](tasks.ko.md#schema-and-migration)를 참고하세요.

## 설치

`install.py`는 Codex에 번들된 개인 마켓플레이스 헬퍼와 `codex plugin add`를
사용합니다. 호스트 로컬 파일 락이 설치를 직렬화합니다. 새 트리는 교체 전에
스테이징되고 검증되며, 이전 트리는 롤백을 위해 보존됩니다. 런타임 상태는
패키징되지도, 업데이트에 의해 제거되지도 않습니다. 선택적인 viewer와 Windows
supervisor 바이너리는 정확한 SHA-256과 함께 로컬에서 제공해야 하며, 업데이트 시
manifest와 실제 바이트를 다시 검증한 뒤에만 보존합니다.

`ccc-viewer`는 별도의 Rust/Ratatui 표시 process입니다. controller database를 직접
열지 않습니다. Python controller가 observation 원장에서 content-free AG-UI JSONL을
stream하고, viewer가 이를 결정적으로 fold한 뒤 제한된 agent card로 투영해 실시간
또는 과거 상태를 그립니다. schema 15는 controller request/receipt 생명주기를 닫힌
content-free operation metadata로 투영하며 경로, argv, 본문, 결과, hash와 error text는
이 경계를 넘지 않습니다. viewer는 compact operation chip, 스크롤 가능한 run/operation
inspector, 결정적 headless 전체 tree와 cursor/run-era replay를 제공합니다. 원장 schema,
privacy filtering과 변경 권한은 계속 Python controller에 남습니다.

공개 저장소는 관리자의 GitHub 핸들만 사용합니다. 머신별 구현 노트, 계정
기록, 자격 증명, 원본 실시간 세션 산출물은 의도적으로 포함되어 있지
않습니다.

## 영속적인 스케줄링

스키마 5는 불변 의존관계 집합, FIFO 큐 항목, 고정된 실행 입력, 추가 전용
이벤트를 추가합니다. `BEGIN IMMEDIATE`는 코디네이터 간의 승인을
직렬화하며, 후보별 세이브포인트(savepoint)는 실패한 검사가 실행 한 건을
소모하지 않도록 합니다. 부모 승인, 결과 무결성, 최종 입력 크기, 실행/태스크/
큐 링크는 원자적으로 커밋됩니다. 워커는 커밋 이후에 시작됩니다. 시작 전
종료는 점유(claim) 만료와 명시적 재시도로 해결되며, 자동 재생(replay)으로
해결되지 않습니다. 알 수 없는 실행은 용량을 계속 점유합니다.

큐에 등록된 프롬프트는 `claude-control.task.v3`를 사용하며, v2 기반과
출처(provenance)가 포함된 복사된 승인 부모 보고서를 함께 담습니다. 자식
이력은 부모 파일을 다시 여는 대신 그 고정된 바이트를 검증합니다. 승인 이전에
부모 리비전이 변경되면 자식은 차단됩니다. `dispatch --until-idle`은
상태를 저장하지 않고(stateless) 유한하며, 기존 워커는 그 데드라인보다 더
오래 실행될 수 있습니다. 실행 상태와 큐/결정 이벤트는 동일한 데이터베이스
트랜잭션 안에 기록됩니다. [큐 시맨틱스](queue.ko.md)를 참고하세요.

## 메시지 선택과 전달

스키마 6은 불변 메시지, 리비전 선택, 순서가 있는 바인딩 영수증에 더해
명시적인 취소 원장(ledger)을 추가합니다. 복합 외래 키가 모든 영수증을
정확한 메시지, 태스크 리비전, 실행에 바인딩합니다. 소스 보고서는 enqueue
시점에 검증되고 복사되며, 이후의 읽기는 소스 산출물을 다시 열지 않습니다.

선택(selection)은 기존의 리비전 트랜잭션을 사용하며, v2 기본 정의는
변경되지 않습니다. 예약 시점에 선택된 메시지는 실체화된 입력을 계약
`claude-control.task.v4`로 확장하며, 의존관계 보고서, 크기 확인, 실행 입력,
실행 예약, 영수증이 함께 커밋됩니다. 검사기는 기본 라운드트립, 고정된 메시지
페이로드, 선택 및 실행 바인딩을 확인합니다. 시작되지 않은 명시적 재시도는
동일한 입력으로 영수증을 추가하고, 실패한 실행된 턴은 의도적인 새 리비전/
재전달을 요구합니다. 워커 실행과 reconciliation은 변경되지 않습니다.

오직 현재 리비전만 예약할 수 있습니다. 이력상의 제출되지 않은 선택은 감사
용도로 보존될 뿐 실시간 디스패치 권한으로 취급되지 않습니다. 이벤트는
단조증가하는(monotonic) 커서 ID를 사용하며, 타임스탬프는 참고용일 뿐 순서나
전달을 보장하지 않습니다.

## P4 워크플로우 템플릿

스키마 7은 워크플로우, 불변 단계(step), 예약 영수증을 추가합니다. 고정된
정책은 워커/검토자 태스크, 기준 ID, 호출/리비전/시간 예산을 고정합니다.
코디네이터는 기존 태스크 트랜잭션, P3 메시지, 범위가 지정된 P2 승인을
사용합니다. 모든 승인은 커밋 시점에 정책을 다시 확인하며, 각 단계는 실패/
시작되지 않음/알 수 없음 시도를 포함해 하나의 영수증을 셉니다.

태스크 v5는 실행 스냅샷을 워크플로우 정책과 정확한 소스 아이덴티티로
확장합니다. 이는 P3 메시지 ID를 통해 고정된 소스 보고서를 참조하므로 모델은
사본 한 개만 받습니다. 구조화된 검토는 모든 기준과 대상 다이제스트를
검증합니다. 템플릿 전용의 reported 엣지는 완전하고 온전한 결과를 요구하며,
일반적인 의존관계 승인은 변경되지 않습니다. 검토 추천은 결코 Codex 승인을
생성하지 않습니다. 중지(stop)는 취소를 요청하기 전에 승인을 영속적으로
닫으며, 알 수 없는 실행은 reconciliation될 때까지 격리됩니다.
[워크플로우](workflows.ko.md)를 참고하세요.

## P5 컨트롤러 중재 워크스페이스

스키마 8은 영속적인 생성 의도(intent), 불변의 정책/태스크 바인딩, 실행
스냅샷, 조작 의도와 영수증, 명령 런처 아이덴티티, 최종 내보내기 해시를
추가합니다. 생성은 파일 시스템 쓰기 이전에 자신의 UUID를 예약합니다. 태스크
v6 봉투는 정책, 트리 인벤토리, 이전 영수증, 남은 예산을 담습니다. 변경되지
않은 Claude 러너는 여전히 네이티브 도구 사용을 거부합니다.

유한한 워크스페이스 코디네이터는 의도를 기록하기 전에 요청된 전체 배치를
검증합니다. 각 조작은 영수증을 생성하며, 중단된 조작은 Codex의 확인을 위해
멈추고 결코 재생(replay)되지 않습니다. 명명된 검사(check)는 모델 실행과
실행 용량을 공유합니다. 그 내부 exec 래퍼는 Bubblewrap에 진입하기 전에
자신의 PID 아이덴티티를 영속화하며, reconciliation은 살아 있는 소유자/
런처를 거부하고, 영수증이 기록된 후에는 지연된 래퍼가 시작될 수 없습니다.
중지 복구는 워크스페이스가 중지되었다고 선언하기 전에 소유 실행 취소를
반복합니다.

Git 블롭은 체크아웃 훅이나 필터 없이 읽힙니다. 소스 파일은 변경되지 않은
채로 유지되며, 정확히 허용된 파일만 비공개 트리에서 편집될 수 있습니다.
검사는 일회용 사본과 고정된 시스템 런타임 마운트를 받으며, 격리된 사용자/
PID/네트워크 네임스페이스와 정제된 환경을 사용합니다. 시간/출력 제한과
프로세스별 rlimit은 제한되어 있으며, 전체 cgroup 할당량은 사용하지
않습니다. 최종 트리, 패치, 매니페스트는 내보내기와 태스크 승인 이전에
재검증됩니다. 읽기 전용 Fable 워크스페이스는 정확히 고정된 출력을 검토할 수
있습니다. [워크스페이스 가이드](workspaces.ko.md)를 참고하세요.
